# Head Pose from Audio — Pipeline Options

## Current state

Facial animations are generated by **LAM_Audio2Expression**, which produces 52 ARKit
blend shape weights per frame from audio input. This covers everything from jaw open
to brow raises to cheek puffs.

**Head rotation is not included.** The ARKit 52 spec (`jawOpen`, `eyeBlink…`, etc.)
does not have head orientation — Apple's Live Face API exposes pitch/yaw/roll as a
separate data channel that LAM simply does not predict.

The gap is filled today by a **procedural approximation** in `side_by_side_scene.html`:
speech energy is derived from `jawOpen` + `mouthFunnel` weights and mapped to a gentle
pitch nod, combined with a slow per-character sinusoidal roll sway. This is convincing
at the camera distances used here, and can be toggled off with `H` for comparison.

---

## Why head pose matters

Even small head movements — a 2–3° tilt while thinking, a nod during emphasis, a
slight turn toward a listener — are primary cues that distinguish "talking" from
"reciting". Without them, avatars read as robotic at close-up framing.

For the side-by-side scene the procedural approach is adequate. For fully authored
scenes with tight scripted emotion beats, authored head motion becomes preferable.

## Options evaluated

### 1. SadTalker
**What it does:** Generates a talking-head *video* from a still image + audio.
Internally it runs two separate networks — one for 3DMM expression coefficients,
one for head pose (pitch/yaw/roll Euler angles per frame).

**Why it's relevant:** The head pose predictor is the part we want. SadTalker's
intermediate output (`coeff_dict`) contains `angles` as a `(N, 3)` array of Euler
angles that map directly to head bone rotation.

**Integration approach:**
1. Run SadTalker on a neutral grey image + the same audio used for LAM.
2. Intercept `coeff_dict['angles']` in `inference.py` before the rendering step.
3. Write a sidecar JSON alongside the LAM output:
   ```json
   {
     "headPose": [
       { "time": 0.033, "pitch": -0.012, "yaw": 0.008, "roll": 0.005 },
       ...
     ]
   }
   ```
4. In `loadFaceJSON`, read `headPose` if present and drive
   `actor.mgr.humanoidBone.head.rotation` the same way morph targets are driven.

**Pros:** Active project, good head motion quality, head pose angles are in world
space and map directly to bone rotation with no conversion needed.

**Cons:** SadTalker's primary output is video. Using it just for pose extraction is
roundabout. Dependency is large (~4 GB model weights). The expression coefficients
(3DMM) are a separate space from ARKit52 and are not needed here.

---

### 2. DiffPoseTalk
**Paper:** *DiffPoseTalk: Speech-Driven Stylistic 3D Facial Animation and Head Pose
Generation via Diffusion Models* (SIGGRAPH 2024)

**What it does:** Predicts both 3D facial expression and head pose from audio using
a diffusion model, outputting FLAME model parameters.

**Why it's not a drop-in:** FLAME expression coefficients (typically 50–100 dimensional)
are a learned basis over a specific 3D mesh. They are not ARKit blend shapes. Mapping
FLAME → ARKit requires a learned or least-squares linear projection trained on paired
data; the conversion is lossy and requires additional tooling.

**Head pose output:** Euler angles per frame — usable directly.
**Face output:** FLAME parameters — not usable without conversion.

**Verdict:** Interesting if starting from scratch, but switching from LAM to DiffPoseTalk
for face data would degrade expression quality. Head pose only could theoretically be
extracted from DiffPoseTalk while keeping LAM for blend shapes, but this means running
two inference pipelines and the added complexity is hard to justify over SadTalker's
extraction approach.

---

### 3. Audio2Head
**Paper:** *Audio2Head: Audio-Driven One-Shot Talking-Head Generation with Natural Head
Motion* (IJCAI 2022)

**What it does:** Generates head motion as dense **optical flow / keypoint
displacements** applied to a source frame to warp a video. There is no bone or blend
shape representation — it is a pixel-level video synthesis tool.

**Why it doesn't fit:** There is no intermediate representation that maps to a head bone
rotation. Extracting usable pose data would require running a separate 3D head pose
estimation model on the generated video frames — a two-step pipeline that introduces
errors at each stage.

**Verdict:** Wrong abstraction level for this pipeline. Ruled out.

---

### 4. GeneFace / GeneFace++ / SyncTalk
NeRF-based talking head systems that produce high-quality synchronized video from audio.
Same fundamental issue as Audio2Head: the output is rendered pixels, not parameters.
Head pose is modelled internally but not exposed as usable data. Not applicable.

## Proposed schema extension

If SadTalker head pose extraction (or a similar tool) is integrated, the face JSON
schema would be extended in-place:

```json
{
  "names":    ["jawOpen", "eyeBlinkLeft", ... ],
  "frames":   [{ "time": 0.033, "weights": [0.0, 0.12, ...] }, ...],
  "headPose": [{ "time": 0.033, "pitch": -0.01, "yaw": 0.005, "roll": 0.003 }, ...]
}
```

`headPose` is optional — if absent, the procedural fallback runs. If present, it
overrides the procedural approach for that clip.

In `loadFaceJSON` and the render-loop tick, head pose would be treated as three
additional channels (pitch → rotation.x, yaw → rotation.y, roll → rotation.z)
applied to `actor.mgr.humanoidBone.head` alongside the morph target tick.

The neck bone would receive a fraction (≈ 40%) of the same rotation to distribute
the motion naturally across the cervical spine.

---

## Recommended next step

Before committing to SadTalker extraction, evaluate whether the procedural nod is
sufficient for the use case at this camera distance. Toggle it off with `H` in
`side_by_side_scene.html` to judge the difference.

If authored head motion is needed, the implementation path is:
1. Add a `--export-pose-json` flag to a thin wrapper around SadTalker inference.
2. Extend `loadFaceJSON` to read the optional `headPose` array.
3. Drive the head bone alongside morph targets in the existing render loop tick.

No changes to `traffic_scene.json`, `scene.html`, or the VRMA pipeline are required.
